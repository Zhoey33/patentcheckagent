# 专利审查 skill 优化记录

2026-09-14，参考 [handsomestWei/patent-disclosure-skill](https://github.com/handsomestWei/patent-disclosure-skill)。只借鉴其结构和工作方法，未复制工具代码或安装其依赖。

## 参考仓库的适用部分

- 以简短 `SKILL.md` 路由到具体规则，按需读取参考资料。
- 申请文件模块把权项、说明书和附图做语义对照，并强调机器对照不等于公开充分。
- 将内容缺口与已确认事实区分，保留原材料依据，避免凭空补造技术事实。

交底书生成、轻量查新、外观线稿、Obsidian 案例库、专利地图与审查意见答复不属于本系统当前的申请材料检查任务，未引入。参考仓库的 OA 模块也包含 PDF 文本抽取，并非不经文件工具就能读扫描件，因此没有沿用其扫描件限制。

## 当前内容的实际问题与改动

| 原有内容 | 问题 | 新规则 |
|---|---|---|
| 说明书必须逐字重复每条从属权利要求，术语不能差一个字 | 把文字重合误当支持关系 | 检查语义、对象和技术关系，只有影响理解/范围时报告差异 |
| 所有功能限定、模型、数值范围都要求固定披露清单 | 不区分公知实现及实际技术贡献，容易误报 | 按实现所需信息判断，说明本案为什么需要某项细节 |
| 要求保证新颖性、体现发明点 | 无对比文件也可能给出实体否定结论 | 无经核实对比证据时明确未评估，不凭部件常见否定组合 |
| 缺少材料时直接套清单 | 未上传与原申请缺失混淆 | 区分未提供、未读完、未找到与已证实问题 |
| 泛泛要求“具体条款”，包含旧条号和地方习惯 | 容易生成错误条号或扩大适用范围 | 提供官方依据入口，未知条款或地方版本明确待核实 |

| 两份 277 行正文并存，使用时拼接 prompt | 内容重复维护，也不是真正的 skill 调用 | 单一 skill 包：入口、权项检查、说明书检查、报告格式、依据边界 |

新版位于 `skills/check-patent/`。两阶段保留，通过稳定特征编号连接；修改规则后，任务应保存完整 skill 快照，以保证执行中不受编辑影响。

## 行为验收重点

1. 文本型 PDF、扫描件 PDF 和 Word 均从原文件交给 Codex；不能只因没有文字层在上传时失败。
2. 不同表述但语义一致的说明书支持不能误报为“未逐字复制”。
3. 只做温度数值显示的方案，不应凭标题“提示”就要求添加报警功能。
4. 只有公知部件而没有对比文件，不应直接给出不具备新颖性的结论。
5. 真正缺少引用基础或存在图文矛盾时，应给出具体原文、位置和修改方向。
6. 不可辨读或未读完的页面，应列出范围限制，不能伪装完成全文检查。

上述是用于行为复核的案例条件；真实调用结果见下方，不把格式校验当作模型行为通过。

## 扫描件验证后的内容调整

两页合成扫描 PDF 的首次真实调用中，模型已读到全部权项，但对清晰数字反复裁剪并以 300/600/1200 dpi 上采样，将字体字距形成的“1 7”列为数值疑点，还对“壳体背面”和普通几何尺寸过度要求定义。针对这些实际行为，补充了：

- 清晰页面读取一次即可，放大仍不清楚则标记限制，避免反复上采样；第二阶段复用已生成页面。
- 区分技术对象缺乏引用基础与已有对象的常用部位/属性。
- 结合原图理解数字字距，不凭空引入小数点、分隔符或极端读法。
- 普通几何量按通常测量含义理解，特殊状态确实影响范围时才要求解释。

这些约束减少无实际影响的疑点，仍要求报告真正的材料冲突。

## 真实 Word 案例的性能排查（2026-09-14）

案例 `c2804d4f-5e8e-45d7-bee0-ddd4d6887309` 使用规则 v2，四份材料均为 Word；权利要求 10 项，权要正文约 2,375 字符、说明书约 5,944 字符，附图 Word 含 PNG/SVG。不是 PDF 扫描识别问题。

原任务排队约 1.2 秒，第一阶段 428.859 秒，第二阶段达到 600 秒上限失败，总计约 17 分 9 秒。已有事件可还原第一阶段 19 次文件命令（1 次失败）、第二阶段 40 次（3 次失败）；按旧事件时间戳计算的工具执行时间合计约 53 秒，远小于任务总耗时。此值为近似值：旧 stdout 读取方式会滞留已经缓冲的事件，不能把所有事件间隔都当成纯模型推理时间。剩余时间包括模型推理、生成、API 往返及重试，旧日志无法进一步准确拆分。

第一阶段累计用量：输入 482,252 tokens（包含多轮重复上下文，缓存命中 428,032）、输出 29,511 tokens，其中推理输出 13,067。输出报告 10,251 字符。报告还列举了 Word 包内的分节符、空脚注等检查过程，存在与技术审查收益不相称的探查。

### 对应改动

- 显式设置 `CODEX_REASONING_EFFORT=low`，保留原 `qwen3.8-flash` 和单阶段 600 秒时限。[阿里云 Responses 文档](https://help.aliyun.com/zh/model-studio/qwen-api-via-openai-responses) 规定 Qwen 3.8 默认 `xhigh`；通过同版 Codex CLI 接入本地模拟端点确认，旧请求仅包含 `reasoning.summary`、未传 `effort`，新请求确实携带 `effort=low`。配置含义参见 [Codex 官方配置参考](https://learn.chatgpt.com/docs/config-file/config-reference)。
- Skill 2.1.0 合并读取、复用带位置笔记、定向补查 Word 内容，避免无关包内结构探查及反复重写报告；仍覆盖全部权项、特征和真实问题，仍将原文件交给 Codex 自行读取。
- 实际复测发现容器缺少 `unzip`，导致命令失败并换工具重读；镜像补齐该工具。
- 修正 stdout 缓冲与半行阻塞问题：后台读取完整事件，主线程独立执行截止时间。旧代码在设定 1 秒期限时，遇到未换行输出会等到 2 秒子进程结束后才报超时；新增回归覆盖半行和批量事件。
- 对持有不可变 Skill 快照的任务，第二阶段重试保留并复用已完成的第一阶段报告。原文件/规则不变，历史无快照任务仍清理旧阶段结果重跑。
- 成功及失败调用均记录耗时，成功调用记录 tokens；工具事件只增加耗时与输出字符数，不留命令正文或文件工具返回正文。

### 同文件复测结果

原机、原模型、同一批四份 Word 原件，使用 `low` 和 Skill 2.1.0，仍分两个独立 Codex 会话执行，未扩大超时时限：

| 指标 | 原失败任务 | 优化后真实复测 |
|---|---:|---:|
| 第一阶段 | 428.859 秒 | 258.340 秒 |
| 第二阶段 | 600 秒后失败 | 247.311 秒，成功 |
| 总时间 | 约 1,029 秒后失败 | 505.651 秒，成功 |
| 文件命令 | 59 次，4 次失败 | 22 次，1 次失败 |
| 第一阶段输入 tokens | 482,252 | 143,025 |
| 第一阶段输出 tokens | 29,511 | 14,472 |

优化后第二阶段用量：输入 345,568（缓存命中 281,472）、输出 12,464（其中推理 6,468）。两阶段报告分别 7,064 和 5,720 字符，均覆盖权项 1–10 的 32 个特征编号；第二阶段关闭了部分已有说明书支持的疑点，报告了摘要 317 字等具体检查结果。复测的一次失败为 `unzip` 缺失，发布镜像已补齐；此轮模型调用仍使用旧容器验证候选代码，不能把补工具后的收益算入这组数字。

这是一份案件上的真实速度对比，不代表所有材料都能在 8 分 26 秒内完成，也不等同于准确率测评。任务时间仍主要取决于模型生成与多轮往返；不以缩减特征覆盖或提高超时时限宣称提速。
