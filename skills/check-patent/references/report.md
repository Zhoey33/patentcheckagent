# 报告格式

按本次指定阶段输出，使用 Markdown 标题和表格。首行必须是对应阶段的一级标题；不要把整个报告包在代码块里。完整流程时顺序包含两个阶段，报告只呈现实际完成的检查。

## 第一阶段

以 `# 第一阶段：权利要求书检查与特征分解` 开始，包含以下三级标题：

### 材料与检查范围

简述已读文件、页码/章节及专利类型依据。存在未读页、乱码或未知类型时列明限制。

### 审查结论

说明实际发现的主要问题和待核对内容。没有实质问题时明确说明，不必制造问题或列出固定数量。

### 问题项

每项使用：

1. **[严重/一般/提示] 问题标题**（已发现问题 / 需确认 / 撰写建议）
   - 原文依据：文件名、页码/章节/权项和必要的短摘录。
   - 判断与影响：解释具体歧义、缺口或冲突；依据区分为法律要求、适用预审要求、技术判断或写作建议。
   - 建议修改：最小修改方向及原文支持位置，需新增事实时说明待确认。

同一原因合并为一项，列出所有受影响位置。严重程度由实际影响决定，不由措辞强弱决定。材料不足的疑点不能直接列为已证实严重缺陷。

### 技术特征分解与需说明书解释项清单

| 特征编号 | 权项及继承关系 | 技术特征摘录 | 需核对的解释与原因 | 支持情况 |
|---|---|---|---|---|

逐项填入实际内容；未读说明书时支持情况写“待第二阶段核对”。覆盖全部新增特征，不为控制表格长度截掉后续权项。

## 第二阶段

以 `# 第二阶段：说明书检查` 开始，包含：

- `### 材料与检查范围`：实际读取的文件/页码；第一阶段结果更正如有单独说明。
- `### 审查结论`：结合两阶段证据，说明可确认的结论和剩余不确定项。
- `### 权要特征-说明书解释对应检查表`：沿用第一阶段编号。

| 特征编号 | 技术特征 | 说明书/附图依据 | 支持情况 | 缺口或说明 |
|---|---|---|---|---|

支持情况使用“已支持 / 部分支持 / 未找到支持 / 无法判断”。“未找到支持”须说明核对范围；“无法判断”说明缺失材料或可读性限制。

- `### 问题项`：沿用上述问题格式，关联特征编号，避免重复第一阶段已解决的疑点。
- `### 附图与摘要检查`：分别说明已检查结果、实际问题或未提供/无法辨读。
- `### 优先修改与待确认事项`：按影响排序列出具体动作及需补充的事实；只有实际存在时才列。

## 严重程度

- 严重：已有清楚证据表明核心方案的实现、保护范围理解或支持存在实质缺口。
- 一般：有依据的局部歧义、材料冲突或形式问题，需要修正但尚不足以认定整个方案有实质缺陷。
- 提示：非强制的清晰表达和保护布局建议。

报告是基于所给材料的辅助检查，不输出授权概率、伪精确总分或无检索依据的授权结论。无需逐项罗列全部通过项，只保留帮助理解结论的已确认事项。
